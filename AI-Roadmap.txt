Phase 2 — LLM fundamentals

You don’t need to become an ML engineer.

For an SDET, understand:

LLM

Large Language Model.

Examples:

* GPT
* Claude
* Gemini
* Llama

Prompt

Instruction/context given to the model.

Tokens

The units the model processes.

Context window

How much information the model can consider in a request.

Temperature

Controls randomness/variation in generation.

Hallucination

When an AI produces information that sounds correct but isn’t grounded in facts.

That last one is very important for testing.

⸻

Phase 3 — AI + Automation

This is where your current framework becomes interesting.

Imagine your test fails:

LoginPage.ts
locator("input[name='username']")

Tomorrow the application changes it to:

<input id="user-name">

Traditional automation:

❌ locator failed
❌ test failed
❌ engineer investigates

AI-assisted automation could potentially:

Test failure
     ↓
Analyze DOM
     ↓
Compare previous locator
     ↓
Identify likely replacement
     ↓
Suggest new locator
     ↓
Engineer approves
     ↓
Update test

This leads into:

Self-healing automation

We’ll study:

* locator healing
* DOM analysis
* AI-generated locator suggestions
* confidence scores
* human approval
* risks of automatically changing tests

And we’ll be careful about the distinction between true self-healing and simply asking an LLM to guess a locator.

Phase 5 — RAG

Then we’ll introduce one of the most important GenAI concepts for enterprise applications:

RAG — Retrieval-Augmented Generation

Instead of asking an LLM:

“What are our application requirements?”

we give it access to your actual:

Requirements
Test cases
API documentation
Architecture documents
Defects
Release notes

Then:

User question
      ↓
Retrieve relevant information
      ↓
LLM
      ↓
Grounded answer

This is much more useful in enterprise QA than a generic chatbot.
